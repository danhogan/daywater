# Fresh native team-screen startup

## What runs

The independent Windows probe constructs the complete original entry7 UI source,
executes its creation and activation scripts, and advances its scheduled scripts
for 160 or 1,000 updates. It reads the original DOL constants, template entry2,
32 team database entries and four fonts directly from private W: files.
It does not load the original module or a savestate during native startup.

The source chooses the initial teams, builds seven-player lineups for both sides,
assigns their formations and fixed poses, changes the team labels/logos, and
produces 14 selected-player preview requests. Those requests retain actual PLAY
identity, model name and raw factory/getter fields. Factory execution and visible
athlete rendering remain separate; a queued request is not a loaded model.

Fresh preparation also exercises all32 teams, both sides and each of the five
TSTR weighting modes:320 cases. Each produces seven distinct roster members and
a valid formation. This is a native consistency check, not320 original gameplay
or menu comparisons.

A diagnostic 854×640 capture also draws the source Select Teams title, both
Chicago logos, Ready labels and Go Back B prompt. It uses the existing host
affine/text rasterizer; original GX projection/filtering/pixels are not verified.
This passive state has no visible athlete models, roster labels or portraits.

## Host choices and limits

Initial weighting mode0 supplies one possible outcome of original801EE24C(0,5).
The original RNG/bootstrap lifecycle is not reconstructed by this host.
No-profile/common-mode6 remains the supported startup branch. Resource effects
are retained requests; archive registration, hardware input, sound and the model
factory are supplied host boundaries.

The root selected bit is seeded by activation. An empty timer queue or a long
passive run does not prove that directional focus, team confirmation, field8
handoff or interactive selection works. Those paths require source input and
joined flow comparisons. The complete original menu startup has not yet been
compared as a single original-engine run.

## Forward-loaded team screen

The default startup described above omits loaded arguments. Original Quick
Game's forward entry supplies `{1,0x69}` to FFFE with separate argumentFFFFFFFF,
then activates with FFFC argument0/no arguments. The explicit native API
`nflstreet_team_screen_start_context` now preserves that distinction and rolls
back source/state on failure. The preview opts in with `--quick-game-start`.

Fresh native Windows runs with that frame can browse both teams and construct
both seven-player lineups through source events. Default sequence7,7,7 gives
teams1/1 and PLAY15; changed sequence4,4,7,4,4,7,7 gives teams31/31 and PLAY318.
Both produce14 athlete requests. This is native integration evidence;
untouched-original whole-startup agreement and subsequent field/match handoff
remain unverified. See [preview scope](team_live_preview.md).

`W:\Daywater\research-temp\nflstreet-team-start-args-20261011\catalog-run16.log`.

its gate is set, queries 14 DIOP targets per side before reading DIGP. The
